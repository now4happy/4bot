# 뮤즈 작업 지시문 — alert-hub 반영

> 아래 전체를 뮤즈에게 그대로 전달하세요. (압축파일 `alert-hub.zip` 과 함께)

---

## 목표

매매봇 5개 + 업데이트봇의 텔레그램 알림을 `alert_hub` 로 모은다.
**긴급(critical)만 즉시 텔레그램**, 나머지는 기록 후 **하루 1회 브리핑**. 봇이 멈추면 watchdog 이 알려준다.
구글 SSH 서버 1대에서 모든 봇이 돌고 있으며, 코드는 GitHub 를 통해 서버에 반영한다.

## 지켜야 할 원칙 (어기지 말 것)

1. **매매·주문·전략 로직은 수정하지 않는다.** 알림 호출(`notify`, `heartbeat`)만 추가한다.
2. **비밀값을 절대 노출하지 않는다.** `.env`, 봇 토큰, API 키는 커밋·로그·채팅·PR 설명에 쓰지 않는다. (`.gitignore` 에 이미 제외돼 있음. 커밋 전 `git status` 로 `.env` 가 없는지 확인)
3. **기존 텔레그램 전송 코드는 지우지 않는다.** 1~2주는 기존 방식과 허브를 **병행**하고, 사용자가 확인한 뒤에만 정리한다.
4. 허브 import 는 반드시 `try/except` 로 감싼다 (`examples/bot_example.py` 형태). 허브가 고장나도 봇은 계속 돌아야 한다.
5. 각 단계가 끝나면 결과를 사용자에게 짧게 보고하고, 막히면 추측하지 말고 물어본다.

## 작업 순서

### 1. 저장소에 반영
- `alert-hub.zip` 압축을 푼다 → `alert-hub/` 폴더. **파일 내용은 수정하지 않는다.**
- 새 저장소 `alert-hub` 로 올리거나(권장), 사용자가 지정한 위치에 둔다.
- `.env`, `data/*.db` 가 커밋 대상에 없는지 확인 후 커밋/푸시.
  커밋 메시지: `feat: alert-hub 알림 허브 추가`

### 2. 서버에 설치
```bash
git clone <저장소> ~/alert-hub   # 이미 있으면 git pull
cd ~/alert-hub
python3 -m venv .venv
.venv/bin/pip install -e .
cp .env.example .env
```
- **`.env` 의 값(토큰, 채팅ID, API 키)은 사용자가 직접 채우게 한다.** 사용자에게 `nano .env` 로 입력하라고 안내하고, 값을 대신 받지 않는다.
- `HUB_BOT_NAMES` 는 실제 봇 이름 6개로 맞춘다. 이 이름이 코드의 `notify("이름", ...)` 와 **정확히 같아야** 한다.

### 3. 설치 검증
```bash
.venv/bin/python -m unittest discover -s tests      # 전부 OK 여야 함
.venv/bin/python -m alert_hub test                  # 사용자 텔레그램에 ✅ 메시지 도착 확인
.venv/bin/python -m alert_hub status
```

### 4. 각 봇에서 허브를 쓸 수 있게 하기
- 각 봇이 쓰는 파이썬 환경에서 `import alert_hub` 가 되어야 한다.
  봇마다 venv 가 다르면 각 환경에서 `pip install -e ~/alert-hub` 실행. (안 되면 `PYTHONPATH=~/alert-hub`)

### 5. 봇 코드 수정 — **먼저 분류안을 사용자에게 보고하고 승인받은 뒤 적용**
1. 봇 6개 코드에서 기존 텔레그램 전송 호출 위치를 전부 찾아 표로 정리한다.
   `봇 | 파일:줄 | 현재 메시지 | 추천 등급`
2. 등급 기준:
   - 🔴 `critical` : 주문 실패, 예외/에러, 손절 발동, 잔고 부족, API/인증 오류, 비정상 종료
   - 🟡 `warning` : 재시도 후 성공, 슬리피지 큼, 잔고 적어짐
   - 🟢 `info` : 정상 체결, 상태 보고, 시작/종료, 업데이트 완료
3. 사용자 승인 후, **기존 전송 코드는 그대로 두고 그 옆에** `notify(...)` 를 추가한다.
4. 각 봇의 **메인 루프에 `heartbeat("봇이름")`** 을 한 줄 추가한다. (자주 불러도 내부에서 30초에 1번만 기록)
5. 업데이트봇처럼 하루 1번만 도는 봇은 `.env` 에서 `업데이트봇:1500` 처럼 무소식 기준(분)을 길게 준다.
6. 봇을 재시작하고, 봇마다 `python -m alert_hub status` 에서 하트비트가 "방금" 으로 뜨는지 확인한다.

### 6. 자동 실행(cron) 등록
- `timedatectl` 로 서버 시간대를 먼저 확인한다 (구글 서버는 보통 UTC).
- `crontab.example` 의 두 줄을 경로/시간만 고쳐 `crontab -e` 에 등록한다.
  - watchdog: 10분마다
  - briefing: 사용자 기준 아침 시각 (서버가 UTC 이면 한국시간 8시 = `0 23 * * *`)

### 7. 완료 확인 체크리스트
- [ ] 단위 테스트 전부 통과
- [ ] `alert_hub test` 로 텔레그램 수신 확인
- [ ] 봇 6개 모두 `status` 에 하트비트 표시
- [ ] `notify 매매봇1 critical "테스트"` 로 즉시 알림 수신 확인
- [ ] `briefing --no-send` 출력에서 6개 봇이 모두 보임
- [ ] `.env` / 토큰이 GitHub 에 올라가지 않았음
- [ ] cron 2줄 등록 확인 (`crontab -l`)

### 8. 사용자에게 보고할 것
- 봇별로 어떤 알림을 어떤 등급으로 연결했는지 표
- 기존 알림은 그대로 유지(병행 중)임을 명시
- 이상/보류 사항

## 롤백
문제가 생기면 봇 코드에 추가한 `notify`/`heartbeat` 줄만 되돌리고(기존 전송 코드는 남아 있음), cron 2줄을 주석 처리하면 원래 상태로 복귀한다. `alert-hub` 폴더 자체는 그대로 둬도 무해하다.

## 1~2주 후 (사용자가 "정리해줘" 라고 할 때만)
브리핑 내용이 실제 상황과 맞는지 사용자가 확인한 뒤, 봇들의 **info/warning 성격의 기존 텔레그램 전송만** 제거한다. critical 성격의 기존 전송은 허브가 안정적으로 동작하는 것이 확인된 뒤 마지막에 정리한다.
