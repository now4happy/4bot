# 공통 작업·업로드·문서 관리

갱신: 2026-10-28 (문서 3종 체계: STATUS.md 자동 · 규칙 문서 · docs/log 기록). 기존 기록을 분리한 문서이며 새 서버 적용의 증거가 아니다.
필수 작업 원칙은 저장소 루트 START.md를 따른다. 아래에서 이번 작업과 관련된 제목만 읽는다.

## 1. 문서 관리와 작업 원칙

- AI는 매 작업 뒤 docs/log/ 에 새 기록 파일을 남기고, 규칙·구성이 바뀐 경우에만 해당 봇 문서의 관련 항목을 고친다. 현재 상태는 STATUS.md(업데이트 비서 자동)가 담당하므로 START.md·봇 문서에 진행 상태를 쓰지 않는다. 같은 설명/로그/코드 전문을 여러 문서에 반복 추가하지 않는다.
- **사용자가 그날 마지막이라고 판단한 최종 MD를 직접 업로드한다. 매번 업로드를 요청하지 않는다.** 코드 배포와 MD 업로드 시점은 별개다. ‘최종본’도 다음 작업에서 계속 갱신한다.
- 예전 전체 기록 `Total rule.md` 는 2026-10-28 docs/archive/ 로 옮겼다. 새 내용을 더하지 않는다.
- 최신 첨부 MD에는 GitHub 미업로드 기록이 있을 수 있다. 더 오래된 저장소 문서로 최신 기록을 덮어쓰지 않는다.
- 확정 규칙은 반복 질문하지 않는다. 요청 변경·실제 코드와의 충돌·진행에 꼭 필요한 미확인 정보만 확인한다. 예시였던 ‘지정가만/일일 -2%/계좌 10%’를 실제 매매 규칙으로 채택하지 않는다.
- 기존 전략·한도·종목·진행일·enabled·환전·키·배포 보호 조건을 관련 요청 없이 바꾸지 않는다. 조회 테스트를 위해 실주문·자동환전·자금이체를 실행하지 않는다. 부족액 알림 후 사용자가 자금을 채운다.
- 변경 전 기준 코드 보존, 문법 및 영향에 맞는 검사 수행. 파일 작성/로컬 검사/사용자 업로드/승인/서버 적용/재시작/원격 동기화/실응답을 구분해 기록한다.
- 비밀키·토큰·계좌 인증·개인키 원문은 문서·채팅·ZIP·GitHub에 넣지 않는다. `update_keys_20261021.py`에는 비밀값이 있다는 이력만 보존한다.
- 사용자 폰·태블릿 SSH 환경을 고려해 필요한 명령을 짧게 나눠 제공한다. 서버에 rg가 없었던 이력이 있으므로 grep/sed/python으로 대체한다.
- 봇 일정은 KST, 미국장은 코드상 시장 시간대, 사용자 현재 현지 시각은 대만(UTC+8), 서버는 UTC를 구분한다.

## 2. GitHub 확인·파일 전달·업로드

전체 운영 코드: https://github.com/now4happy/4bot . AI가 직접 최신 main과 관련 파일/import/호출 관계를 읽는다. 전체 코드를 사용자에게 복사 요청하지 않는다. GitHub에 없는 서버 설정·실응답만 최소 요청한다.

1. 최신 main 기준으로 수정·검사한 코드 파일과 MD를 제공한다. AI는 별도 요청 없이 push·PR·서버 적용·Telegram 승인을 하지 않는다.
2. 사용자가 staging 또는 최신 main에서 만든 승인용 브랜치에 **변경 Python 파일만** 업로드한다. `bot_office/*.py`는 `bot_office` 안에 올린다. ZIP 자체나 중복 `bot_office/bot_office` 폴더를 올리지 않는다.
3. MD(규칙 문서·docs/log 새 기록)도 같은 staging 에 올린다. STATUS.md 는 업데이트 비서가 쓰므로 올리지 않는다. main 직접 업로드 안내는 폐기됐다.
4. 업로드를 마친 뒤 Telegram `6. Update`에 `업데이트 확인` → 새 알림의 대상·브랜치·파일 확인 → 사용자가 ✅ 승인한다. 추가 업로드 전의 오래된 버튼을 재사용하지 않는다.
5. updater가 보호조건/미기록 변경/문법을 확인하고 병합·복사·재시작·건강검사·실패복구·버전기록 후 main에 결과를 올린다. docs-only 승인에는 봇 재시작/버전 증가가 없을 수 있다.
6. 사무실 updater는 `bot-office.service`를 재시작한다. 별도 상시 비서의 코드 변경이 반영되면 필요한 경우 다음 서비스만 재시작한다. 매번 전체 거래봇을 재시작하지 않는다.

```bash
sudo systemctl restart bot-office-secretary.service
```

업데이트 scan 기본 주기 300초, `업데이트`/`업데이트 확인`/`/update`로 강제 scan. 알림은 branch SHA에 묶여 있어 변경/삭제되면 재조회가 필요하다. 새 offer 뒤 ‘새 수정 없음’ 메시지가 함께 나올 수 있으므로 실제 새 대상/파일을 본다.

Git 복구: 미기록 변경·MERGE_HEAD·충돌을 보존하고 상태를 먼저 확인한다. 강제 push/reset으로 덮어쓰지 않는다. 모바일 병합은 `--no-edit` 사용. 과거 main 문서 직접 수정과 서버 staging 코드가 갈라져 main push만 실패했으나 서버 코드는 실행됐다. 사용자가 진행 중 병합을 `git commit --no-edit`로 완료한 뒤 `git push --atomic origin HEAD:main HEAD:staging`으로 양쪽을 `16772b6`에 동기화한 이력이다. 현재 상황을 확인하지 않고 이 복구 명령을 반복하지 않는다.

## 문서 유지 방식

- START.md: 최대50줄, 읽는 순서·필수 원칙·문서 경로만. 진행 상태는 쓰지 않는다(STATUS.md 자동 · docs/log 기록).
- 봇별 문서: 현재 규칙/구성/진행 상태의 담당 원문. 관련 제목 범위만 조회한다. 전체 코드 복사 금지.
- docs/archive/Total rule.md: 2026-10-28 까지의 보존용 전체 기록. 새 내용을 더하지 않으며 평상시 통독하지 않는다. 상세 과거 원인/증거가 필요하면 키워드·제목을 검색해 해당 범위만 읽는다.
- 실제 코드/설정은 GitHub/서버가 원문이다. 문서에 코드 전문·전체 로그를 다시 복제하지 않고 파일 경로·기준 커밋·관찰한 검사 결과만 둔다.
- 새 채팅은 현재 작업의 문서1개부터 읽고, 실제 의존성이 생겼을 때 추가 문서를 읽는다. 이미 읽은 파일은 변경/모순/누락이 없으면 같은 내용 재조회하지 않는다.
- 안전 확인·서버 배포 확인·필요한 주문 경로 검증은 읽기 비용을 줄이기 위해 생략하지 않는다. 테스트 수를 늘리기 위한 반복 검사는 하지 않는다.
- 최신 첨부와 저장소 문서의 갱신 시점이 다르면 서로 다른 최신 사실만 병합한다. 새 첨부의 미배포 기록을 오래된 main으로 지우지 않는다.
- 문서만 바꾼 작업에서는 새 코드 작성·실계좌 조회·전체 저장소 스캔·테스트를 자동으로 시작하지 않는다.
- 문서 ZIP은 배포용 코드 ZIP과 별개다. START.md 는 저장소 루트, 규칙은 docs/handoff/, 작업 기록은 docs/log/ 에 같은 경로로 올린다.
- 문서 GitHub 업로드는 사용자가 최종본이라고 판단할 때만 한다. 새 채팅에서 START.md만 첨부하는 방식은 상세 문서가 조회 가능한 위치에 올라간 뒤에 쓴다. 그 전에는 이번 작업 상세 MD만 추가 첨부한다.
