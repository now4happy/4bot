# Total rule · 운영 프로그램 통합 인수인계

갱신: 2026-10-25. 중복을 통합한 현재 기준본. 실제 배포 상태와 과거 코드 검토 결과는 구분한다.

## 1. 문서 관리와 작업 원칙

- AI는 매 작업마다 필요한 새 정보·결정·변경·검증·오류·복구·미완료를 판단해 **같은 문서에 누적 반영**한다. 같은 내용이나 비슷한 설명은 추가하지 않고 해당 항목을 최신 상태로 갱신한다. 고유한 매매 규칙·운영 정보·미해결 위험은 삭제하지 않는다. 과거 원문을 통째로 반복 보관하지 않는다.
- **사용자가 그날 마지막이라고 판단한 최종 MD를 직접 업로드한다. 매번 업로드를 요청하지 않는다.** 코드 배포와 MD 업로드 시점은 별개다. ‘최종본’도 다음 작업에서 계속 갱신한다.
- 실제 저장소 파일명은 루트의 `Total rule.md`다(대문자 T·공백). 다운로드용 `Total_rule.md`는 링크 호환 이름이므로 GitHub에서는 기존 파일을 같은 이름으로 교체한다. 루트란 저장소를 처음 열었을 때의 최상위 목록이다.
- 최신 첨부 MD에는 GitHub 미업로드 기록이 있을 수 있다. 더 오래된 저장소 문서로 최신 기록을 덮어쓰지 않는다.
- 확정 규칙은 반복 질문하지 않는다. 요청 변경·실제 코드와의 충돌·진행에 꼭 필요한 미확인 정보만 확인한다. 예시였던 ‘지정가만/일일 -2%/계좌 10%’를 실제 매매 규칙으로 채택하지 않는다.
- 기존 전략·한도·종목·진행일·enabled·환전·키·배포 보호 조건을 관련 요청 없이 바꾸지 않는다. 조회 테스트를 위해 실주문·자동환전·자금이체를 실행하지 않는다. 부족액 알림 후 사용자가 자금을 채운다.
- 변경 전 기준 코드 보존, 문법 및 영향에 맞는 검사 수행. 파일 작성/로컬 검사/사용자 업로드/승인/서버 적용/재시작/원격 동기화/실응답을 구분해 기록한다.
- 비밀키·토큰·계좌 인증·개인키 원문은 문서·채팅·ZIP·GitHub에 넣지 않는다. `update_keys_20261021.py`에는 비밀값이 있다는 이력만 보존한다.
- 사용자 폰·태블릿 SSH 환경을 고려해 필요한 명령을 짧게 나눠 제공한다. 서버에 rg가 없었던 이력이 있으므로 grep/sed/python으로 대체한다.
- 봇 일정은 KST, 미국장은 코드상 시장 시간대, 사용자 현재 현지 시각은 대만(UTC+8), 서버는 UTC를 구분한다.

## 2. GitHub 확인·파일 전달·업로드

전체 운영 코드: https://github.com/now4happy/4bot . AI가 직접 최신 main과 관련 파일/import/호출 관계를 읽는다. 전체 코드를 사용자에게 복사 요청하지 않는다. GitHub에 없는 서버 설정·실응답만 최소 요청한다.

1. 최신 main 기준으로 수정·검사한 코드 파일과 MD를 제공한다. AI는 별도 요청 없이 push·PR·서버 적용·Telegram 승인을 하지 않는다.
2. 사용자가 staging 또는 최신 main에서 만든 승인용 브랜치에 **변경 Python 파일만** 업로드한다. `bot_office/*.py`는 `bot_office` 안에 올린다. ZIP 자체나 중복 `bot_office/bot_office` 폴더를 올리지 않는다.
3. MD를 올릴 때도 같은 승인용 브랜치의 루트 기존 `Total rule.md`를 교체한다. main 직접 업로드 안내는 폐기됐다.
4. 업로드를 마친 뒤 Telegram `6. Update`에 `업데이트 확인` → 새 알림의 대상·브랜치·파일 확인 → 사용자가 ✅ 승인한다. 추가 업로드 전의 오래된 버튼을 재사용하지 않는다.
5. updater가 보호조건/미기록 변경/문법을 확인하고 병합·복사·재시작·건강검사·실패복구·버전기록 후 main에 결과를 올린다. docs-only 승인에는 봇 재시작/버전 증가가 없을 수 있다.
6. 사무실 updater는 `bot-office.service`를 재시작한다. 별도 상시 비서의 코드 변경이 반영되면 필요한 경우 다음 서비스만 재시작한다. 매번 전체 거래봇을 재시작하지 않는다.

```bash
sudo systemctl restart bot-office-secretary.service
```

업데이트 scan 기본 주기 300초, `업데이트`/`업데이트 확인`/`/update`로 강제 scan. 알림은 branch SHA에 묶여 있어 변경/삭제되면 재조회가 필요하다. 새 offer 뒤 ‘새 수정 없음’ 메시지가 함께 나올 수 있으므로 실제 새 대상/파일을 본다.

Git 복구: 미기록 변경·MERGE_HEAD·충돌을 보존하고 상태를 먼저 확인한다. 강제 push/reset으로 덮어쓰지 않는다. 모바일 병합은 `--no-edit` 사용. 과거 main 문서 직접 수정과 서버 staging 코드가 갈라져 main push만 실패했으나 서버 코드는 실행됐다. 사용자가 진행 중 병합을 `git commit --no-edit`로 완료한 뒤 `git push --atomic origin HEAD:main HEAD:staging`으로 양쪽을 `16772b6`에 동기화한 이력이다. 현재 상황을 확인하지 않고 이 복구 명령을 반복하지 않는다.

### 5.3 3번 토스 주식들 스마트적립 — 확인된 기준 코드

2026-10-24 제공된 GitHub main의 `main.py`, `t_ui.py`를 내려받아 확인했다. 이후 서버·main이 바뀔 수 있으므로 현재 파일과 충돌하면 최신 실제 코드를 우선한다.

종목별 설정:
- `currency`: KRW 여부로 한국/미국 분류.
- `enabled`: 종목별 자동매매 켜짐/중지.
- `base_amount`, `s_mode`, `s_day`, `s_target_days`, `last_exec_date`, `sold_stage`, `has_held`.
- 전체 전원: `is_master_active`.
- 초기 화면 기준 기본 매수금: 한국 100,000원, 미국 40달러. 종목별 변경 가능. 현재 실제 투자금이라고 단정하지 않는다.

사이클:
- `buy_1`: 1차 100일 분할매수.
- `pause`: 지정 N일 정지 대기. enabled이고 실행 조건을 통과하면 일차만 증가.
- `buy_2`: 지정 N일 2차 분할매수.
- `sell`: 지정 N일 분할매도.
- `decision`: 기간 종료 후 다음 단계 결정 대기. 자동주문 건너뜀.
- 기간 완료 후 N일 정지/N일 분할매도/N일 2차매수를 사용자가 선택한다.
- 시작 버튼은 enabled=True로 설정한다. 즉시 주문 명령이 아니다. 전체 전원·시간·사이클·잔고 조건을 계속 적용한다.
- 중지 버튼은 신규 자동주문 차단용. 이미 접수한 주문 취소나 보유주식 청산 기능이 아니다.

매수:
- 수익률이 +1% 이상이고 평단·보유수량이 있으면 기준금액의 1/2, 그 외 기준금액 1배.
- 한국 정수 수량: `max(1, int(buy_amt // cur_p))`; 현재가가 없을 때 1주로 처리하는 기존 코드가 있었다. 따라서 기준금액이 엄격한 최대 한도라고 보장하지 않는다. 이 부분은 이번 UI 변경에서 수정하지 않음.
- 미국 매수: `smart_us_buy()` → 기존 주석상 달러 금액 매수와 관련된 API 사용. 정확한 주문 체결 방식·시장가/지정가 속성은 API 구현 확인 필요.
- 미국 달러 부족 검사는 익절 판단 뒤 수행한다. 달러가 부족해도 보유주식 익절 매도는 가능하도록 의도됨.
- 달러가 필요액보다 부족하면 주문 대신 실패 사유 기록. 사용자 자금 보충을 기다린다.

익절:
- 기본 `tp1_pct=10`, `sr_pct=20` (설정 가능).
- 수익률 10% 이상 20% 미만이고 1차 미실행이면 당시 잔고의 20% 매도.
- 20% 이상 30% 미만이고 2차 미실행이면 당시 잔고의 20% 매도.
- 30% 이상은 해당 기준 코드에서 추가 익절 없음. 화면도 미정/매도 없음으로 안내.
- 손실권으로 내려갈 때마다 물타기 배수를 늘리는 별도 규칙은 이 기준 코드에서 확인되지 않음. 하락 중 정기 분할매수와 2번의 물타기 전략을 섞지 않는다.
- 손절 로직은 확인되지 않았다.
- 한국 익절 수량은 정수이며 1주 이상·보유수량 이내 계산, 미국은 소수 수량 반올림 계산.

분할매도:
- 남은 일수 `max(1, target_days - day)` 기준으로 잔고를 나눔.
- 한국은 정수 수량으로 최소 1주·보유수량 이내.
- 미국은 소액/마지막 날 전량, 그 외 소수 수량 분할하는 기존 코드.

중복 주문·상태 보존:
- 종목 `last_exec_date`가 해당 시장 현지 오늘이면 실행 건너뜀.
- 매수 주문 식별자 `b_{today_str}_{sym}`. 익절 `tp{stage}_{today_str}_{sym}`, 분할매도 `s_{today_str}_{sym}`.
- 같은 식별자 사용 의도가 있어도 API가 중복을 항상 차단한다는 보장은 별도 검증되지 않았다.
- 매수 요청이 비-`API HTTP` 예외로 끊기면 체결 가능성을 고려해 당일 재주문 금지로 기록하고 일차는 증가시키지 않음. 토스 앱 확인·필요 시 진행일 보정 안내.
- `save_merged()`는 최신 설정을 다시 읽고 매매 진행 키만 합쳐 저장한다. 텔레그램에서 도중 변경한 enabled/금액 등을 덮어쓰지 않으려는 코드.
- 주문 직전 `stock_trade_allowed()`로 전체·종목별 상태 재확인. 이미 전송된 주문 취소나 원자적 중지 보장은 아니다.
- `has_held`가 있고 잔고가 0으로 판단되면 종목을 설정에서 제거하는 기존 흐름이 있음.

거래 시각:
- 한국: 코드상 한국시간 평일 11:00~15:00 사이 재시도, 11:15 이후 미진행 알림 확인.
- 미국: 코드상 `EST_TZ`의 평일 11:30~15:50 사이 재시도, 11:45 이후 미진행 알림 확인.
- scheduler 반복 대기 50초. 전체 `last_retry_ts` 및 실패 알림에 의한 재시도 제어도 있음.
- 이번 최신 t_core.py에서 EST_TZ=ZoneInfo("America/New_York") 확인(DST 반영). 과거 두 파일만 보고 정의 미확인으로 남겼던 항목은 갱신한다.
- `check_holiday()`가 호출되지만 확인한 scheduler에서는 휴장 안내에 사용되며 거래 실행 자체를 막는 조건으로 연결되지 않았음. 공휴일 거래 차단이 완성됐다고 단정하지 않는다.

화면의 일차:
- 기존 목록/상세에서 s_day=0이고 보유가 있으면 `auto_detect_cycle_days()`로 추정하던 코드가 있었다.
- 함수는 주문 이력을 시도하고, 없으면 보유금액/기준금액으로 일차를 추정하는 기존 구현을 화면에서 확인.
- QLD 1주가 2/100일로 보였던 것은 실제 2거래일 매수의 증거가 아니다.

### 확정 동작

- 사용자 요청: 6. Update에서 **이번 업데이트 대상 봇만** 제어. 모든 운영 봇을 무조건 끄지 않는다. 여러 대상은 ‘이번 업데이트 대상 전체 중지 대기’ 버튼 또는 대상별 버튼으로 요청하고, ‘이번 대상 거래 재개’/대상별 재개 버튼으로 해제한다.
- 잔고는 예수금이 아니라 **관리 종목의 보유 수량**을 뜻한다. 보유가 있으면 30초 주기로 조회한다. 대기 중 기존 전략의 매수·매도는 계속되므로 자연 청산이 없으면 계속 기다릴 수 있다. 강제 매도·주문 자동 취소는 하지 않는다.
- 보유 수량0 및 미체결/예약 없음이 확인되면 신규 매수·매도·정정 요청을 차단하고 알림. 기존 취소/조회 기능 자체는 유지한다. 알림의 ‘업데이트 진행’을 다시 눌러야 배포한다. 중지 요청 자체는 업데이트 승인이 아니다.
- 업데이트 후에도 차단 유지, 사용자가 재개 버튼으로 해제. 재개는 기존 master/power/enabled/종목 설정을 켜거나 초기화하는 것이 아니라 업데이트용 차단만 해제한다. 실패·충돌·재시작 뒤에도 파일에 저장된 차단을 유지한다. `거래 상태` 또는 `/pause_status`로 대기·중지 상태와 재개 버튼을 다시 볼 수 있다.
- 기존 매매 시간 보호는 기본 유지. **실제 차단 부품 실행·관리 수량0·주문 없음 재확인에 성공한 대상만** 해당 업데이트에서 시간 보호를 넘길 수 있다. 조회 오류·누락·NaN·연속조회 미완료·미체결은 0으로 취급하지 않는다. 장기 보유 봇은 조건을 만족할 때까지 업데이트가 계속 보류된다.
- 일반 잔고 폴링은 주문 잠금을 잡지 않는다. 0 후보를 찾으면 대상의 공유 주문 잠금에 배타 잠금을 잡아 진행 중 API 전송 완료를 기다리고 보유/미체결을 재검사한 뒤 중지 파일을 원자 저장한다. 동시 신규 주문과 중지 전환 사이의 틈을 막는다. async 주문은 취소돼도 배경 요청이 끝날 때까지 잠금 유지.
- 폴링 목표는 30초 주기이며 API 응답 지연·잠금 경합이면 실제 확인은 늦어질 수 있다. 네트워크 오류 안내/중지 알림은 성공 후 기록해 반복을 줄이고, 오류 중에는 대기 유지. 정확히 한 번의 Telegram 전달은 보장하지 않는다.

2. 첫 단계의 정상 기동을 확인한 뒤 `update_pause_bot_hooks_20261025.zip`을 푼다. 원하는 봇 폴더의 파일을 **그 봇별로 묶어서** staging 같은 위치에 올리고 새 알림으로 승인한다. 필요한 봇부터 하나씩 설치해도 된다. 전부 지원하려면 1~4번 모두 설치한다. 파일 한두 개만 빼먹으면 새 import가 실패하므로 아래 묶음을 지킨다.

3. **첫 거래봇 부품 설치/재시작은 기존 업데이트 보호 조건이 허용되는 때에만** 진행한다. 아직 실행되지 않은 차단 장치로 장중 재시작을 안전하다고 확인할 수 없으므로 최초 한 번은 제한을 우회하지 않는다. 거래봇 부품을 아직 안 올린 단계에서 중지 버튼을 누르면 ‘차단 부품 먼저 설치’로 거절하는 것이 정상이다.
4. 설치 후 이후 업데이트부터 새 offer의 중지 대기 → 수량0 알림 → 업데이트 진행 → 완료 후 재개. 다중 대상 중 일부만 중지됐다면 나머지도 조건을 충족해야 전체 업데이트 가능하다.
5. ZIP 자체/임의 상위 폴더를 올리지 않는다. 키/설정/장부 파일은 포함하지 않는다. MD는 사용자가 그날 최종본으로 판단할 때 업로드한다.
